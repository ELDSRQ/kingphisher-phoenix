## Part 1 — Senior developer review of build, architecture, and code

### 1.1 What is genuinely good

- **Fail-closed is pervasive and consistent.** Unknown roles grant no
  capability; missing/unknown capability `require()` denies; a provider
  configuration drift fails the canary; a model-id mismatch rejects the whole
  AI response before persistence; a disabled source's in-flight fetch is
  discarded under a DB lock; training bindings fail delivery closed. This is
  the single most valuable property of the codebase and it is *uniform*.
- **The outbox pattern is the right backbone.** Business mutation + audit/queue
  intents commit in one transaction; dispatch is separate and retryable; a
  crash leaves a visible pending row, never a silent loss or an
  in-memory-only queue request. Combined with crash-aware delivery claims
  (`QUEUED → SENDING` with attempt UUID), duplicate provider contact is
  structurally prevented.
- **The generation contract is exemplary for an AI boundary.** The module
  docstring states the threat model (attacker-influenced feed → prompt
  injection), sanitization happens *before* the model call, outbound context
  is deliberately much smaller than generated content, and the response model
  proposes *content only* — never an approval, recipient, schedule, or send.
  `_bounded_ai_json` + byte-capped streaming + Pydantic re-validation at the
  HTTP boundary is exactly right.
- **The tracking edge is a model of a public boundary.** 5 real endpoints + a
  static landing page + a 410 tombstone. Per-token (5/min), per-IP (60/min),
  and global (3,000/min) rate limits with attacker-controlled strings
  rejected *before* bucket allocation; trusted-proxy-only XFF chain walking
  from the direct-proxy side; body/request-target limits; hardening headers
  on early errors; CSP `default-src 'none'` on training pages; purpose-scoped
  training bearers with server-side answer comparison (the correct index
  never reaches the recipient).
- **Delivery is genuinely two-phase.** Canary cohort → evidence-bound full
  publication, with manifest hash, provider+config hash, expiry, drift
  detection, and crash-aware claims — all re-validated *inside* the worker
  under a DB lock before any provider side effect. RoE is signed,
  domain-constrained, and refusal is per-recipient at schedule.
- **Migration discipline.** 33 migrations with least-privilege grants,
  retention constraints mirrored in ORM metadata, and a
  fresh-install/historical profile that passed 92 tests. The `0029` canary
  gate, `0030` privacy notice uniqueness, `0031` ledger, `0032` quarantine,
  `0033` knowledge check are all coherent.
- **Honest evidence labeling.** The project repeatedly refuses to overclaim:
  "A returned job ID is a request reference, not a status link"; "destination
  MTA handoff is not inbox delivery"; "current snapshots are not causal
  evidence"; "these are implemented capabilities, not proof that an Azure
  tenant … has been qualified live." This discipline is rare and worth
  protecting.

### 1.2 Build criticism

1. **Monolith modules are past the pain threshold.**

   | File | Lines |
   |---|---|
   | `apps/operator-api/src/kp_operator_api/routers.py` | 5,418 |
   | `apps/operator-api/src/kp_operator_api/console.py` | 4,154 |
   | `apps/operator-api/src/kp_operator_api/deployment_orchestration.py` | 3,112 |
   | `apps/workers/src/kp_workers/jobs.py` | 2,809 |
   | `apps/operator-ui/src/console/app.js` | 6,792 |
   | `apps/operator-api/src/kp_operator_api/main.py` | 752 |

   A 5,400-line router file means one `git blame` hop to touch any
   campaign/recipient/source/domain concern. `jobs.py` at 2,809 lines mixes
   generation, delivery, mailbox, retention, alerts, reminders, and directory
   sync. This is the #1 maintainability debt and it will produce collisions in
   parallel-agent work.

2. **The UI is one 6,792-line file with no build step, no package.json, no
   framework, and no frontend test runner.** Served raw via `StaticFiles`. The
   only UI tests are Python string-containment contract tests (26 files
   reference `app.js`) plus a shell/asset test. There is no DOM-level
   behavioral test, no Playwright, no jest. A 6,792-line imperative
   DOM-building file with zero behavioral coverage is the largest untested
   surface in the system — and it is the *operator control plane*.

3. **Doc drift was present at review time** (fixed in commit accompanying this
   doc): `docs/architecture/README.md` asserted head `0032` (actual `0033`),
   `README.md` said "eight worker roles" (actual nine), and both described
   ANA-010/TRN-010 items as unimplemented after they landed. The handoffs
   (`NEXT_SESSION_HANDOFF.md`, `WAVE-BUILD-PLAN.md`) were current; the
   architecture README and README were not.

4. **Empty scaffolding existed:** `infrastructure/cloudflare/` and
   `infrastructure/policies/` contained zero files and zero tracked entries —
   removed with this review.

5. **The delivery provider is a fork in one function.** `_make_batch_sender`
   branches SMTP vs ACS; `email_provider == "azure_communication_services"`
   checks appear in ~6 places in `jobs.py`. Provider selection is string-typed
   at call sites rather than a resolved strategy object. Works, but this is
   the kind of duplication that produces the "F-1 lesson" class of bug
   (updating one producer, missing consumers).

6. **`_CountingResponse` was introduced mid-stream** (AI-010) because the
   bounded JSON reader consumes the stream exactly once; the wrapper is
   correct and well-commented, but it is evidence of the original design not
   planning for metrics. Not a bug — a smell.

7. **`views["azure-deployment"]` uses bracket notation while every other view
   uses dot notation** — cosmetic inconsistency; harmless today.

8. **Test distribution skews toward the server.** 26 app.js-string contract
   tests can pin prose strings, which breaks on copy edits and provides
   *negative* protection (asserting something is *not* present). Fine as
   guardrails; not a substitute for behavior tests.

### 1.3 Bugs and correctness findings (verified in code)

- **Console CSP vs. inline styles — a real defect, now fixed and pinned by
  tests.** `_CONSOLE_CSP = "default-src 'none'; script-src 'self';
  style-src 'self'; connect-src 'self'; img-src 'self'"` (no `'unsafe-inline'`,
  no `'unsafe-eval'`). Investigation resolved the question on both halves:
  - **Delivery: verified.** The operator security middleware stamps the CSP
    on every response whose path starts with `/console`, and middleware wraps
    the router including the StaticFiles mount — the SPA does receive its
    policy. A new contract test
    (`apps/operator-api/tests/test_console_csp_contract.py`) asserts the
    exact header on `/console/`, `/console/app.js`, and `/console/styles.css`.
  - **Handlers: CSP-clean by design.** `el()` routes every `on*` key to
    `node.addEventListener(k.slice(2), v)`, never an inline HTML attribute,
    so `script-src 'self'` is compatible. The initial suspicion that inline
    `onclick:` attributes would break the console was disproven.
  - **Styles: a real, minor defect.** `el()` passes the `style:` key through
    to `node.setAttribute("style", ...)` — an inline style attribute, which
    the console's own `style-src 'self'` (no `'unsafe-inline'`) silently
    blocks. Five call sites were found (the review initially counted four):
    four template-preview frames (`max-height: 55vh` / `45vh`, the
    desktop/mobile `preview-frame` box) and the preview dialog
    (`max-width: 900px` via `setAttribute`). In a CSP-enforcing browser these
    would render unstyled — a functional defect in the operator's most-used
    review surface, not a security hole. **Fixed** by moving all five into
    `styles.css` classes (`.template-body.tall` / `.template-body.medium` /
    `.preview-frame.mobile` / `.preview-frame.desktop` / `.modal-wide`) and
    using `classList.add` for the dialog. The contract test now also asserts
    no `style:` key or `setAttribute("style", ...)` remains in `app.js`, that
    `index.html` carries no inline script/handler/style, and that the CSP
    value stays free of `'unsafe-inline'`/`'unsafe-eval'`.
  - **Residual:** this is deterministic evidence, not a live-browser check.
    The browser/WCAG qualification lane must still confirm the rendered page
    under a real CSP-enforcing browser (the README honestly says "browser
    execution remains unqualified"), but the question is now reduced to a
    confirmation rather than an unknown.
- **`_ip_rate_limited` uses `_client_ip(request) or "unknown"`** as a limiter
  key — a shared bucket for any IP-unresolvable request. Acceptable (an
  attacker cannot spoof a trusted-proxy chain), but under a misconfigured
  ingress all clients collapse into one 60/min bucket.
- **Rate-limit backend defaults to `memory`** (`rate_limit_backend: ... =
  "memory"`). In a multi-replica managed deployment, memory-backed limiters
  are per-replica — token limiters are fine (tokens are per-recipient anyway)
  but the **global 3,000/min limit becomes per-replica**, weakening it
  linearly with replica count. The Redis backend exists but is not the
  default. Flag for the managed topology.
- **`ACS delivery pacing is not configured` raises `RuntimeError`** in
  delivery — fail-closed, correct, but a `DeliveryConfigurationError` would
  keep operator logs greppable.
- **`check_spf_for_mailbox` runs per-message in delivery** — verify it is
  cached per batch, not per recipient; if per-recipient, that is an avoidable
  DNS cost at scale.
- **`azure-deploy.yml` is 2,756 lines in one file.** Even with the
  orchestration server guarding dispatch, this is a review liability; the
  workflow itself re-runs the hermetic suite (good), but the size makes drift
  between workflow and Terraform (`main.tf` 1,560 lines) hard to audit.

### 1.5 Architecture assessment vs. stated goals

Against the documented objective (one 125-person tenant, two IT staff, threat-
informed campaigns, RSA conference), the design is **appropriate and mostly
right-sized**, with three structural observations:

1. **Three deployables + 13 packages is more seams than a 2-operator product
   needs, but each seam is a security boundary** and the product sells on
   security claims — keep them; do not consolidate for tidiness.
2. **The single-worker supervised process is right for the fleet** (one image,
   one health gate, per-role isolation available as an option).
3. **The weak link is the UI layer**, not the servers: a 6,792-line untested
   file controlling the plane is the single largest gap between
   "architecturally sound" and "operationally trustworthy."

## Part 2 — Security analyst review (UI, features, email, Azure, UX)

### 2.1 Security posture — strong, with the UI caveat

**Strong points (verified):**

- OIDC: JWKS/signature/iss/aud/exp/nbf all checked; `oid` preferred over
  `sub`; issuer-origin-bound discovery with DNS-pinned TLS, redirects/proxy/
  HTTP2 disabled; cross-origin auth redirects fail before navigation; PKCE.
- Secrets: never logged, redacted centrally, excluded from AI context,
  `CipherText` at rest with keyring + prior-key rotation; gitleaks + bandit +
  semgrep + trivy + pip-audit in CI (with recorded scopes).
- SSRF resistance: `kp_sanitization.fetcher` pinned URL resolution; alert
  webhooks HMAC-signed with hostname allowlists; GitHub gateway fixed-origin
  `api.github.com` with host/scheme/port/userinfo/path checks; OIDC/JWKS
  bounded streaming.
- Audit: append-only chain, database-controlled dispatcher, create-only WORM
  anchor to Azure Blob, verification publishes only aggregate status + bounded
  problem count.
- Privacy: pseudonymous 1,826-day ledger, 365-day raw retention, keyed
  verifiers at rest, exports POST-only + `no-store`, single-tenant scope that
  rejects rather than fakes.
- Emergency stop: persistent singleton with reasoned release; kill-switch
  routes exist and are capability-gated.

**The single biggest security finding is the operator console CSP question**
(see 1.3). The console is a high-value target; if its CSP is silently not
applied to static responses — or applied but incompatible with inline
`onclick` — the control plane is missing its main browser-layer defense. This
must be verified with a real browser.

**Secondary findings:**

- The AI model pin is honestly labeled "not a cryptographic attestation" — the
  model ID is self-reported. Acceptable as a config guard; do not market it as
  provenance.
- `rate_limit_backend = memory` default weakens the global limiter per-replica
  in managed mode (see 1.3).
- No brute-force lockout on operator login beyond OIDC — correctly delegated to
  the IdP.
- `POST /console/restart` writes a marker file — capability-gated
  (MANAGE_ROLES); verify it emits an audit event.

### 2.2 UI/UX critique — dense but honest

**Strengths:** server-derived capabilities drive navigation and actions (no
stale-client gating); the two-person-approval rule is stated up front in a
banner (the right instinct); policy banners everywhere ("Delivery fails
closed", "Interpretation boundary") — the UI never lets the operator believe a
handoff is a delivery or a snapshot is a trend. Template preview deliberately
renders plain-text fallback rather than faking HTML rendering.

**Weaknesses:**

1. **17 top-level nav items** (Dashboard, Campaigns, Programs, Executive
   trends, Domains & RoE, Recipients, Sources, Patterns, Template review,
   Training lessons, Privacy, Failed jobs, Audit, Settings, Setup wizard,
   Azure deployment, Help). For a two-person IT team this is a wall of
   options; UX-010 (navigation simplification) is *deferred* — it should be
   promoted because it directly serves the "two IT staff" objective.
2. **"Executive trends" renders tables, not graphs.** **Resolved.** There was no
   canvas/SVG chart code in the UI — the "five-year click/no-click trend graph"
   was a `<table>` of monthly rows. Now `ledgerTrendChart` renders an accessible
   SVG grouped-bar chart (confirmed/heard-click/no-click by month) slotted above
   the retained table, built with a CSP-safe `svg()` helper (`createElementNS`,
   presentation attributes only — never an inline `style=`). Pinned by
   `test_console_csp_contract.py:test_chart_*` and executed offline by
   `apps/operator-ui/tests/chart-smoke.mjs`.
3. **Mixed mental models:** the volume of gated buttons with tooltip
   explanations ("Create and review a current directory preview first") shows
   the workflow complexity is near the ceiling for point-and-click. The
   Directory preview/apply/discard flow, canary→full two-phase publication,
   and approval facets are correct but cognitively heavy.
4. **Good touches worth keeping:** unsaved-form guards, `aria-live` status
   regions, skip-link, focus management on wizard steps, `no-store` where it
   matters, honest error strings without stack leaks.

### 2.3 Feature alignment with objectives

| Objective | Status | Verdict |
|---|---|---|
| Threat-informed campaign content | Sources + patterns + generation contract | ✅ Built; AI execution unproven |
| Realistic-but-safe simulation | ICS without fake URLs, plain-text previews, no credential collection | ✅ Excellent |
| Measurable improvement | Ledger, trends, repeats, confirmed-vs-observed distinction | ✅ Built; chart landed |
| Training loop | Lesson library + knowledge check + 72h due + reminders | ✅ Built (TRN-010) |

| Delivery honesty | SMTP/ACS/Mailpit/M365 matrix, receipts | ✅ ACS unqualified live |

**Enhancement opportunities (prioritized):**

1. **Accessible trend charts (SVG + table fallback)** — **DONE** (see 2.3 #2).
2. **A "Where is my campaign?" timeline** — a single per-campaign vertical
   timeline (draft → reviewed → canary → evidence → published → recalled)
   with evidence status inline would collapse a dozen tooltip-gated buttons
   into one readable story.
3. **Scheduled reports** (deferred today) — for a two-person team,
   "email me the monthly trend CSV" is higher value than most new features;
   the alert/webhook infrastructure exists to build it cheaply.
4. **Guided "first campaign" after onboarding** — the onboarding wizard
   sequences identity → directory → email → mailbox → AI → training → alerts;
   a follow-on guided first-campaign flow would close the loop.
5. **Un-defer the navigation simplification (UX-010)** — group the 17 items
   into ~5 clusters (Run, People, Content, Integrate, Govern).

### 2.4 Email integration review

The provider matrix is a genuine strength: **ACS = recommended managed send;
SMTP = advanced; Graph = directory/report ingestion only; no false "any
provider" claims; Mailpit for dev.** Sender-persona resolution, SPF checks,
delivery pacing for ACS, provider correlation headers, Event Grid receipt
ingestion with authenticated bearer + HMAC binding before Redis — production-
grade thinking. The gaps are all *qualification* gaps (live ACS domain, receipt
ingestion, M365 mailbox polling with real credentials — all unrun), not design
gaps. One design note: the fork-y `email_provider` string checks should become
a resolved provider strategy object (see 1.2.5).

### 2.5 Azure deployment review

DEP-010 (strong defaults + Advanced classification) is a real improvement:
20+ resource-ID/GitHub/Terraform internals collapsed behind a disclosure,
visible inputs seeded from strong defaults, honest "Most operators never
change them" copy, production plan-action blocked until gates verify. The
three-stage timeline (foundation_bootstrap → foundation_finalize → workloads)
with stage evidence is the right shape. GitHub's protected environment remains
the final approval boundary; the browser can never supply a
command/path/repo/ref/credential. **Critique:** the orchestration server +
2,756-line workflow + 1,560-line main.tf is a lot of machinery, and none of it
has ever run against a real tenant — "the guardrails are excellent, the path
is untested." The live qualification lanes (browser login discovery, live
progress/cost/rollback) remain the honest next step. Also: the wizard's
`suggested_default` seeds values captured on submit — the strong-defaults
feature must be verified end-to-end in a real browser (contract tests pin the
schema, not the rendered form).

   browser/WCAG lane must still confirm the rendered page under a real
   CSP-enforcing browser, but that is now a confirmation, not an unknown.

3. **Delete or document empty scaffolding** — done (removed
   `infrastructure/cloudflare/`, `infrastructure/policies/`).

4. **Add one behavioral UI test harness** — even a minimal DOM test (node + a

## Bottom line

A seriously well-built, unusually honest system — the security architecture and
fail-closed discipline are above the norm for this product category, and the
evidence labeling is a model. The gaps concentrate in three places: **the
untested 6,792-line UI** (its CSP question is now resolved at the code level —
five inline style attributes fixed and the contract pinned by tests; the
browser/WCAG lane must still confirm live, and behavioral UI coverage remains
absent), **qualification** (all 8 lanes unrun — known and honestly disclosed),
and **modularization** (monolith files past the maintainability threshold).
Split the monoliths at the file level, render actual charts, add behavioral UI
tests, and run the gates.
