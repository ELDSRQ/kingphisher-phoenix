# Ciphertext legacy-recovery contract

This is not a managed active-key rotation feature. The Azure wizard handles
only non-secret key identifiers and a versionless Key
Vault secret resource ID. Raw decrypt-only keys must be entered directly into
the deployment Key Vault by an authorized platform administrator. They must
never be pasted into the application GUI, GitHub variables, workflow inputs,
Terraform variables, or plan files.

The external secret value uses the runtime's bounded format:
`retired-key-id=<64-hex-key>`, with at most four comma-separated entries. Apply
these exact Key Vault tags before submitting the workloads phase:

- `kp-ciphertext-format=kpct-rotation-v1`
- `kp-ciphertext-prior-key-ids=<canonical comma-separated IDs>`
- `kp-ciphertext-active-key-id=<current active ID>`

The protected workflow checks that the reference exists in this deployment's
vault, is enabled and unexpired, and has the reviewed tags. It also compares
the requested IDs to the existing Terraform outputs: prior IDs cannot be
silently removed, and the active ID cannot change. Terraform independently
marks the active key resource `prevent_destroy`, so a direct plan also refuses
replacement. Terraform then gives only the operator and worker identities
access to the external recovery secret. Container Apps resolves the same value
into both runtimes, preventing operator/worker keyring drift.

The lifecycle comparison runs before both foundation and workload plans. A
brand-new foundation may establish its first active ID because no state exists;
after that, every GUI dispatch must preserve it. `prevent_destroy` is the
independent safety boundary for direct Terraform use and also means teardown
requires an explicit, reviewed removal of that lifecycle protection.

Residual limitations are explicit:

- The existing active key is generated by Terraform, so active key material is
  still present in protected Terraform state and its history. This wave keeps
  the separately prepared prior-key value out of new Terraform variables,
  plans, and state; eliminating historical active-key material requires a later
  move to an external active-key lifecycle.
- Active-key rotation is deliberately unavailable. Independent Container Apps
  roll at different times; a one-apply ID/key change would let a new revision
  write ciphertext an old revision cannot identify. A future safe design must
  pre-stage the exact future key into every old and new revision, prove that
  readiness, and only then promote writes in a separate reviewed dispatch.
- Tags prove reviewed metadata, not the secret's contents. Runtime parsing and
  authenticated decryption fail closed, but there is no pre-deployment database
  decrypt canary yet.
- There is no bulk re-encryption tool. The GUI workflow therefore refuses to
  remove previously configured prior IDs until a separately reviewed rewrite
  and verification gate exists.
